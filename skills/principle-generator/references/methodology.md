# Principle 方法论

本文件是 principle-generator 的核心知识库。生成任何 principle 前先读这里。

---

## 一、什么是 Principle（定位）

Principle 是 AI 算法评测中的**判定基准文档**：把模糊的业务标准，转化成算法、标注、评测三方共用的、可量化可复现的判断依据。

- **算法**按 principle 开发模型 / Agent / prompt
- **标注**按 principle 执行人工标注
- **评测**按 principle 判定对错、构造评测集

三方用的是**同一份**基准。这是 principle 存在的全部意义——它消除了"什么算对"这个问题上的分歧。

### 谁来产出
- **产品主导输出**，算法和评测共同审核对齐。
- 这个 skill 是在替"评测"角色出**初稿**，帮产品把活干一半。**初稿不是定稿**，必须经三方对齐。
- 时序要求：principle 共识应在**算法方案评审阶段**完成，**不得晚于评测数据集构造开始**。

### 什么任务需要 principle
只有**有客观对错**的判别类任务才需要：分类、打标签、是非判断、意图识别、违规检测、信息抽取等。

开放生成、摘要、改写、对话质量这类**主观任务**不靠 principle，靠人审 rubric（评分量表）。遇到主观任务输入，明确告知用户"这类任务不适合用 principle，建议用评分 rubric"，然后停止。

## 二、一份合格 Principle 的最小要素

来自评测规范，每个判别任务至少包含：

| 要素 | 说明 | 没有它会怎样 |
| --- | --- | --- |
| **任务定义** | 在判断什么，一句话讲清 | 标注者各理解各的 |
| **正例边界（✅）** | 什么算命中 | 漏标 |
| **负例边界（❌）** | 什么不算，**且应归到哪个相邻标签** | 误标、标签打架 |
| **触发词 / 信号** | 关键词、语义信号 | 标注者抓不住重点 |
| **对比 label（消歧）** | 和相邻易混淆标签怎么划界 | 易混淆标签互相串 |
| **典型案例** | ✅ / ❌ 例句 | 边界停留在抽象描述 |
| **争议案例** | 模糊地带怎么判 | 争议反复返工 |
| **特殊场景规则** | 层级规则、默认值、优先级 | 边角情况无依据 |
| **输出格式 / schema** | 标签值、字段、是否抽取实体 | 算法输出和评测对不上 |

## 三、消歧方法论（principle 质量的核心）

**边界靠对比定义，不靠孤立定义。** 一个标签的定义写得再漂亮，如果没说清它和相邻标签怎么划界，标注和算法照样会串。

### 三种消歧手段（按强度递增）

1. **❌ 负例 + 去向**：每条"不包括"必须写"→ 应归到 X 标签"。
   - 反例（差）：`❌ 不包括：预算不够的情况`
   - 正例（好）：`❌ 不包括：自身预算不够（→ 顾虑超过购车预算）`

2. **对比标签块**：在易混淆标签下专门列 `对比标签：→ 标签A：区别是… → 标签B：区别是…`。

3. **优先级 / 顺序规则**：当多个标签可能同时命中，明确"先判哪个""命中即停"。
   - 例：战败检测"按顺序检查所有 Principle，命中任一即为正常战败"。
   - 例：安全类"碰撞优先识别为顾虑安全；自燃/热失控优先识别为顾虑电池安全"。

### 易混淆标签要打标记
在多标签体系里，给互相容易串的标签显式标 `易混淆`，提醒标注者格外小心。识别易混淆对的方法：**标签树上相邻的兄弟节点、触发词有重叠的、语义场景相近的**，都是高风险对。

### 资金类 / 时机类经典混淆（来自顾虑标签实例，可作消歧范式参考）
- "车价超预算" vs "钱没凑齐/款没到账" vs "贷款月供压力" vs "嫌优惠不够"——四个完全不同的标签，靠"是预算缺口 / 时间问题 / 流动性 / 政策不满"四个维度区分。
- "等现款改款" vs "等全新车型" vs "等新品上市再决策"——靠"在售车更新 / 全新产品线 / 主动挂起决策"区分。

写消歧规则时，先找出这类"看起来都像、实则不同维度"的簇，逐一划维度。

## 四、缺口检查清单（Step 2 用）

PRD 几乎一定有缺口——它通常只给正例和粗定义。逐项扫描，把命中的整理成《待产品确认清单》追问产品：

- [ ] **缺负例**：只说了什么算，没说什么不算？
- [ ] **缺去向**：说了不算，但没说该归到哪个标签？
- [ ] **触发条件重叠**：两个标签的触发词 / 场景有交集，没说优先级或谁优先？
- [ ] **层级模糊**：多级标签没说"必须识别到第几级"、"什么时候停在上级"？
- [ ] **提到没处理**：文档提到某情况（如"已购竞品""自述是同事"）但没给判定规则？
- [ ] **默认值缺失**：边角输入（信息不足、模糊表述）默认归到哪？
- [ ] **输出格式未定**：标签值是什么？要不要额外抽取实体（如对比的具体品牌车型）？0/1 还是枚举？
- [ ] **争议案例空白**：有没有产品自己都拿不准的灰色案例？这些最该问。
- [ ] **时间 / 业务知识依赖**：判断是否依赖外部知识（如车型发布周期、是否直营模式）？这些假设要写进文档。

**追问原则**：清单按优先级排——先问会导致标签互相打架的边界，再问争议案例，最后问特殊场景。一次别问太多，先问最关键的。用户答不了的，文档里用 `⚠️ 待确认` 标出，绝不静默假设。

## 五、格式选择

| 信号 | 选表格对齐表 | 选 Skill-prose |
| --- | --- | --- |
| 标签数量 | 多（>5 个） | 少（1~4 个判别任务） |
| 层级 | 深（多级标签树） | 浅 / 无 |
| 主要矛盾 | 标签互相易混淆 | 单任务内部的正负例 + 排除 |
| 典型场景 | 顾虑标签体系、意图分类 | 违规检测、战败判定、是非检测 |
| 消费者 | 偏标注 / 评测对齐 | 偏算法（可直接当 prompt / skill 用） |

- 拿不准、或两者都沾边 → 默认表格对齐表（信息密度高、对比直观）。
- 也可以**混用**：主体用表格，复杂单任务用 prose 块展开。
- 用户明确指定就听用户的。

## 六、Principle 质检清单（Step 4 用，交付前逐项核对）

- [ ] **每个标签都有 ✅ 正例 + ❌ 负例**，不只有定义。
- [ ] **每条 ❌ 负例都标了去向**（→ 应归到哪个标签）。← 最常见漏项，重点查。
- [ ] **每个易混淆标签都有对比标签块**，相邻标签互相能划清。
- [ ] **触发词具体**，不是"相关表述"这种空话。
- [ ] **多级标签写清了识别到第几级的规则**。
- [ ] **有优先级 / 命中顺序**（当存在多标签可同时命中时）。
- [ ] **例句来自真实语料风格**，不是干巴巴的造句；✅ 和 ❌ 例句成对出现、对比鲜明。
- [ ] **输出 schema 明确**：标签值、字段、是否抽取实体、0/1 还是枚举。
- [ ] **特殊业务规则显式写出**（如"直营模式默认本品车主"这种依赖业务知识的）。
- [ ] **争议案例有交代**，没交代的标 `⚠️ 待确认`。
- [ ] **带版本管理**：版本号、日期、三方定版签字位。
- [ ] **没有静默假设**：所有靠推断填的内容，要么问过产品，要么标了 `⚠️ 待确认`。

## 七、迭代与版本管理

Principle 不是一次性产物，会随 badcase 反馈持续迭代。

- 每次改动都要**定版**：记录定版内容、日期、产品/算法/测试三方是否同意。
- 改动要可追溯：写清这一版相对上一版改了什么（如"新增车主定义：直营模式下找售后/保养/激活钥匙的默认为本品车主"）。
- 版本号放文档末尾或表格内。模板已内置签字位。
