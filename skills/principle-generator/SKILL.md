# Principle Generator

## 这个 skill 做什么

把 PRD / 业务需求文档 / 标签体系，转化成一份**评测 Principle 文档**。

Principle 是 AI 算法评测里的"判定基准"——对于分类、判断、标注这类**有客观对错**的任务，它把模糊的业务标准变成算法、标注、评测三方共用的、可量化可复现的判断依据。一句话：**算法按 principle 开发，标注按 principle 执行，评测按 principle 评判。**

## 何时使用

- 用户提供 PRD / 业务文档 / 标签清单，希望产出 principle
- 任务是分类、打标签、是非判断、意图识别、违规检测等"有客观对错"的判别类任务
- 需要给一套标签体系补齐定义、边界、消歧规则、案例

**不适用**：开放生成、摘要、对话质量等没有客观对错的主观任务（这类任务靠人审 rubric，不靠 principle）。遇到这种输入，明确告诉用户并停止。

## 核心原则（务必内化）

1. **Principle 由产品主导、算法和评测共审**。这个 skill 是在替"评测"出初稿，最终须三方对齐。初稿不是定稿。
2. **边界靠对比定义，不靠孤立定义**。一个标签写得再清楚，如果不说清它和相邻标签怎么划界，就没用。**消歧规则（对比 label）是 principle 质量的核心**，比定义本身更重要。
3. **PRD 几乎一定有缺口**。PRD 通常只给正例和粗定义，缺负例边界、争议案例、特殊场景规则。识别这些缺口并追问产品，是这个 skill 最大的价值，不要用想象去填。
4. **Principle 同时定义输出 schema**。判断规则之外，要明确产出格式（标签值、字段、0/1、需额外提取的实体等）。
5. **Principle 会迭代，要做版本管理**。每份文档带版本号、日期、三方定版签字位。

## 工作流

### Step 1 — 读输入，抽取判别任务

读完用户提供的 PRD/文档，列出其中所有**判别类任务**。对每个任务，先在脑子里填这张表（信息来自文档的就填，没有的留空待追问）：

- 任务名 / 标签名（含层级路径，如果是多级标签体系）
- 任务定义（在判断什么）
- 正例特征（✅ 什么算）
- 负例边界（❌ 什么不算，且应归到哪个相邻标签）
- 触发词 / 关键信号
- 相邻易混淆标签（对比 label）
- 特殊场景规则（层级识别规则、默认值规则、优先级规则等）
- 输出格式（标签值 / 字段 / 是否需额外提取实体）

如果文档是多标签分类体系，**务必画出标签树**，相邻节点之间最容易混淆，是消歧规则的重点。

### Step 2 — 识别缺口，追问产品（关键步骤，不要跳过）

把 Step 1 表里的空白和模糊点，整理成一份**《待产品确认清单》**，然后**暂停，把清单交给用户**。清单按优先级排：先问会导致标签互相打架的边界问题，再问争议案例，最后问特殊场景。

判断缺口的检查项见 `references/methodology.md` 的「缺口检查清单」。典型缺口：

- 只有正例没有负例边界
- 两个标签的触发条件有重叠，没说优先级
- 多级标签没说"识别到第几级"的规则
- 提到某情况但没说怎么处理（如"已购竞品算什么"）
- 没说输出格式

除非用户明确说"先按你的假设生成、我事后批量审"，否则**等用户回答后再进入 Step 3**。用户回答不了的，在文档里用 `⚠️ 待确认` 标出，不要静默假设。

### Step 3 — 选格式，生成文档

两套格式，按任务类型选（也可由用户指定）：

- **表格对齐表格式** → 适合**多标签分类体系**（标签数量多、层级深、互相易混淆）。模板见 `assets/template-table.md`，写法规范见 `references/format-table.md`。
- **Skill-prose 格式** → 适合**单任务 / 少数几个判别任务**（如违规检测、战败判定）。模板见 `assets/template-prose.md`，写法规范见 `references/format-prose.md`。

拿不准就读 `references/methodology.md` 的「格式选择」。生成时严格套用模板结构，逐条对照 Step 1/2 的信息填充。

### Step 4 — 自检，再交付

对照 `references/methodology.md` 的「Principle 质检清单」逐项核对生成结果。**最关键一条：每个标签的负例 ❌ 是否都指明了"应归到哪个相邻标签"**——这是最常见的漏项。

### Step 5 — 落地

- 默认写出本地 `.md` 文件到工作目录，文件名含标签体系名和版本号。
- 文档末尾带版本 / 日期 / 三方定版签字位（见模板）。
- 若用户要回写飞书：用 `docx_builtin_import`（lark-openapi-mcp）把 markdown 导入为飞书文档。注意当前 token 可能缺 `docx:document` 写权限——先尝试，失败则把权限申请链接给用户，并保留本地 .md 兜底。
